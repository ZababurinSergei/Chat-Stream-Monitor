# Руководство по CHANGELOG.md

Этот документ описывает, как вести [CHANGELOG.md](./CHANGELOG.md) в репозитории `@infoenergo/infoenergo-ui`.

## Зачем нужен changelog

Changelog фиксирует **изменения, важные для потребителей библиотеки**: разработчиков приложений, которые подключают пакет и обновляют версии.

Сюда не попадают внутренние правки, рефакторинг без изменения публичного API, правки тестов, stories и документации для разработчиков библиотеки — если они не влияют на использование компонентов снаружи.

## Формат

Файл следует [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/) и [SemVer](https://semver.org/lang/ru/).

Структура:

```markdown
## [Unreleased]

### Добавлено
### Изменено
### Устарело
### Удалено
### Исправлено
### Безопасность

## [0.0.7] — 2026-06-25
...
```

Разделы **Устарело**, **Удалено** и **Безопасность** добавляйте только когда в релизе есть соответствующие изменения. Пустые разделы не создавайте.

## Раздел `[Unreleased]`

Все изменения текущей ветки/спринта сначала пишутся в `[Unreleased]`.

При выпуске версии:

1. Переименуйте `[Unreleased]` в `[X.Y.Z] — ГГГГ-ММ-ДД` (дата релиза).
2. Создайте новый пустой блок `[Unreleased]` вверху файла.
3. Обновите `version` в `package.json`.

Пример:

```markdown
## [Unreleased]

## [0.0.7] — 2026-06-25

### Добавлено
- **AiDataTable** — ...
```

## Какие разделы использовать

| Раздел | Когда использовать |
|--------|-------------------|
| **Добавлено** | Новые возможности, пропы, события, экспортируемые типы |
| **Изменено** | Изменение поведения существующего API, визуальные изменения темы |
| **Устарело** | API ещё работает, но будет удалён в следующих major/minor |
| **Удалено** | Удалённый публичный API (если не помечали как устаревший — можно указать здесь или в **Изменено**) |
| **Исправлено** | Исправления багов с точки зрения потребителя |
| **Безопасность** | Уязвимости и их устранение |

### Несовместимые изменения (breaking changes)

Для библиотеки на SemVer breaking changes — это повод увеличить **major** (при `1.x.x`) или, на этапе `0.x.x`, как минимум **minor** с явным предупреждением.

В записи обязательно помечайте: **Несовместимое изменение.** — в конце пункта в разделе **Изменено** или **Удалено**.

Пример:

```markdown
- **AiDataTable** — `meta.api.get` теперь строка, а не функция. **Несовместимое изменение.**
```

## Как формулировать записи

Changelog читает **разработчик приложения**, который подключает библиотеку. Пишите с его точки зрения: что увидит в UI, что нужно поменять в своём коде при обновлении версии.

1. **Один пункт — одно изменение для потребителя** (поведение, проп, событие, внешний вид).
2. **Начинайте с компонента или области**, с которой работает потребитель (`**AiDataTable**`, `**Тема**`).
3. **Опишите эффект**: что делать при миграции, если API изменился.
4. **Используйте имена публичного API**: пропы, события, поля `meta`, экспортируемые функции (`initGlobalSettings`).
5. **Не упоминайте внутренности библиотеки**: composables, дефолтные константы, тесты, stories, имена внутренних хелперов.

Хорошо:

```markdown
- **AiDataTable** — `meta.toolbarItems` для своих кнопок в тулбаре; по клику — событие `toolbar-action` с `id` кнопки.
- **AiDataTable** — в `meta.api` передаются строковые пути эндпоинтов, а не функции; HTTP настраивается через `initGlobalSettings`. **Несовместимое изменение.**
```

Плохо:

```markdown
- Обновлён useToolbarConfig.
- DEFAULT_ELEMENTS переименован в DEFAULT_ITEMS.
- Редактор selector использует tableApi.data вместо useFetch.
- Поправлены тесты useDataStore.
```

Внутреннюю реализацию (`useFetch` → `tableApi`) переводите в язык потребителя: «загрузка справочника идёт через тот же глобальный `tableApi`, что и таблица».

## Что документировать

**Документируйте:**

- изменения пропов, событий, слотов, `defineExpose`;
- изменения типов в публичных `types.ts` и экспортах пакета;
- изменение контракта API (`meta.api`, форматы ответов сервера);
- визуальные изменения темы и токенов, заметные в приложении;
- исправления багов, с которыми мог столкнуться потребитель.

**Не документируйте:**

- composables, утилиты и константы, не входящие в публичный API пакета;
- переименования внутри библиотеки, если снаружи контракт не изменился;
- правки unit-тестов, stories, MDX (если не меняют то, как потребитель использует компонент);
- технические детали реализации («вызов перенесён в другой модуль»).

**Проверка:** если потребитель не может или не должен ничего делать с этой информацией — пункт в changelog не нужен.

## Связь с версией в package.json

| Тип изменения | SemVer (после 1.0.0) | На этапе 0.x.x |
|---------------|-------------------|----------------|
| Breaking change | MAJOR | MINOR + пометка в changelog |
| Новая функциональность | MINOR | MINOR |
| Исправление бага | PATCH | PATCH |

Текущая версия пакета указана в `package.json`. Записи в `[Unreleased]` относятся к **следующему** релизу.

## Рабочий процесс

1. Внесли изменение, влияющее на потребителя — **в том же PR** добавьте пункт в `[Unreleased]`.
2. Перед релизом пройдитесь по diff с предыдущей версией и убедитесь, что все breaking changes и новые фичи отражены.
3. При релизе перенесите `[Unreleased]` в секцию с номером версии и датой.
4. При необходимости кратко продублируйте ключевые breaking changes в описании MR/релиза в GitLab.

## Проверка перед мержем

- [ ] Есть ли несовместимые изменения? Помечены ли они?
- [ ] Затронуты ли несколько компонентов — у каждого свой пункт или один обобщающий?
- [ ] Формулировки понятны без чтения diff?
- [ ] Нет ли записей про чисто внутренние правки?
